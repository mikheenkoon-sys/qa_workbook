# Основы Contract Testing

**Contract testing** — это подход, при котором два сервиса (или компонента) проверяются на соответствие заранее согласованному **API-контракту**. Контракт фиксирует, какие запросы отправляет один сервис и какие ответы ожидает получить от другого.

## Зачем это нужно

Представьте систему из нескольких сервисов: `web-app` обращается к `loan-service`, тот — к `user-service` и `payment-service`. Команды работают независимо и деплоят свои сервисы по отдельности. Что может пойти не так?

- Команда `loan-service` переименовала поле `amount` → `loanAmount`. Их unit- и integration-тесты зелёные, но `web-app` в production перестаёт показывать сумму.
- Consumer ожидает `id` как число, а provider начал отдавать строку (UUID).
- Provider удалил «неиспользуемое» поле, которым на самом деле пользовался мобильный клиент.

Классическое решение — **E2E-тесты** на общем стенде. Но они медленные, хрупкие, требуют поднять всю систему сразу и плохо показывают, *где именно* проблема. Contract testing закрывает эту дыру точечно: проверяется **только граница между двумя сервисами**.

## Роли: consumer и provider

| Роль | Что делает | Примеры |
|------|------------|---------|
| **Consumer** | Вызывает API и использует ответ | Frontend, mobile app, другой микросервис |
| **Provider** | Предоставляет (обслуживает) API | Backend-сервис, REST API |

Один и тот же сервис может быть provider для одних компонентов и consumer для других. Например, `loan-service` — provider для `web-app` и одновременно consumer для `payment-service`. Для каждой такой пары существует **свой контракт**.

## Что такое контракт

Контракт — это набор **interactions**. Каждая interaction описывает:

1. **Запрос** consumer: method, path, headers, query, body.
2. **Ожидаемый ответ** provider: status, headers, body.
3. (Опционально) **предусловие** — состояние данных на стороне provider.

Важно: контракт описывает не весь API provider, а только **ту часть, которую реально использует конкретный consumer**.

## Где contract testing в пирамиде тестирования

```
          /\          E2E            — мало, медленные, дорогие
         /  \
        /----\        Contract tests — граница между сервисами
       /      \
      /--------\      Integration    — сервис + его зависимости
     /          \
    /------------\    Unit           — много, быстрые, дешёвые
```

Contract-тесты по сути **заменяют часть integration/E2E-тестов**, которые проверяли только совместимость двух сервисов.

## Contract testing vs E2E

| | Contract testing | E2E |
|---|---|---|
| Что проверяет | Границу взаимодействия двух сервисов | Весь пользовательский сценарий |
| Окружение | Изолированное, детерминированное | Полноценное (много сервисов, UI, БД) |
| Скорость | Секунды | Минуты и дольше |
| Flaky-риск | Низкий | Высокий |
| Локализация проблемы | Точно указывает, какой контракт нарушен | Нужно искать причину по всей цепочке |

> Контрактные тесты **не заменяют** E2E во всех случаях: они не доказывают, что вся система работает целиком, а лишь что конкретная пара consumer ↔ provider совместима. Хорошая стратегия — **много** контрактных тестов и **несколько** ключевых E2E-сценариев.

## Что contract testing НЕ делает

- Не проверяет бизнес-логику provider (это работа unit/integration-тестов).
- Не проверяет производительность и безопасность.
- Не проверяет UI и пользовательские сценарии целиком.
- Не гарантирует корректность данных — только их **форму** и **тип**.

## Когда подходит, а когда нет

**Хорошо подходит:**

- микросервисы и распределённые системы с независимыми релизами;
- frontend ↔ backend, mobile ↔ backend;
- несколько consumers у одного provider;
- сервисы разных команд.

**Менее полезно:**

- монолит, где все изменения деплоятся вместе;
- один consumer и один provider в одной команде и одном репозитории (хватит integration-тестов);
- публичный API с неизвестными consumers (там лучше OpenAPI + schema-валидация).

## Почему passing consumer test — это ещё не всё

Consumer test обычно работает с **mock provider**. Он проверяет, что consumer правильно формирует запрос и обрабатывает ожидаемый ответ. Но то, что настоящий provider действительно отвечает именно так, доказывает только **provider verification**. Нужны **обе** половины.

## Словарь терминов

| Термин | Значение |
|--------|----------|
| **Contract / Pact** | Набор зафиксированных interactions между consumer и provider |
| **Interaction** | Одна пара «запрос → ответ» |
| **Mock provider** | Заглушка provider, которую Pact поднимает в consumer test |
| **Provider verification** | Воспроизведение interactions на реальном provider |
| **Provider state** | Предусловие данных на стороне provider |
| **Matcher** | Правило сравнения по типу/формату, а не по значению |
| **Pact Broker** | Хранилище контрактов и результатов верификации |
| **can-i-deploy** | Проверка, безопасно ли деплоить конкретную версию |

## Итоги

- Контракт = согласованные ожидания consumer к запросам и ответам provider.
- Contract testing проверяет границу взаимодействия, а не весь пользовательский flow.
- Нужны обе половины: consumer test (формирует ожидания) и provider verification (проверяет их на реальном сервисе).
- Это дополнение к пирамиде тестов, а не замена E2E.
