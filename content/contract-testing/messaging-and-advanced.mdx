# Асинхронные сообщения и другие протоколы

Contract testing не ограничен REST. Те же идеи применимы, когда сервисы общаются через очереди, события или другие протоколы.

## Message pacts (асинхронные сообщения)

Если сервисы обмениваются сообщениями через **Kafka, RabbitMQ, SQS, SNS** и т. п., то роли те же, но смысл другой:

| REST | Messaging |
|------|-----------|
| Consumer вызывает API | **Consumer** обрабатывает сообщение из очереди |
| Provider отвечает на запрос | **Provider** (producer) публикует сообщение |
| Interaction = запрос + ответ | Interaction = **описание сообщения** (payload и metadata) |

Важно: **consumer** здесь — тот, кто **читает** сообщение, а не тот, кто его отправляет. Контракт описывает, какие сообщения consumer **умеет обработать**.

### Как это работает

1. **Consumer side**: тест описывает ожидаемое сообщение (например, `LoanApproved` с полями `loanId`, `approvedAt`) и проверяет, что **handler consumer'а** корректно его обрабатывает. Записывается pact-файл с message-interactions.
2. **Provider side**: verification запускает код, который **формирует** это сообщение, и сравнивает его с контрактом.

Брокер сообщений (Kafka и т. п.) при этом **не нужен** — Pact проверяет только содержимое сообщения, а не доставку.

### Особенности

- Нет HTTP-статусов и путей — только **payload** и **metadata** (headers, key, topic).
- Matchers работают так же: типы и форматы, а не конкретные значения.
- Provider state по-прежнему используется, чтобы подготовить данные для генерации сообщения.
- Эволюция схемы событий особенно важна: старые consumers могут обрабатывать события, опубликованные месяцы назад.

## Синхронные сообщения (gRPC и др.)

Для gRPC, GraphQL и других протоколов существуют плагины Pact (**Pact Plugin Framework**), позволяющие описывать контракты поверх Protobuf и других форматов. Идея прежняя: consumer фиксирует ожидаемый вызов и ответ, provider верифицирует.

## GraphQL

GraphQL имеет свои особенности:

- Один endpoint (`POST /graphql`), поэтому в контракте важнее **query** и **variables**, а не path.
- Consumer фиксирует **только поля**, которые запрашивает — это естественно совпадает с идеей CDC.
- Следите за тем, чтобы контракт не превращался в проверку всей схемы.

## Contract testing и другие виды тестов API

| Вид теста | Что проверяет | Дополняет контракты? |
|-----------|---------------|----------------------|
| **Unit** | Логику одного модуля | Да — быстрый базовый слой |
| **Integration** | Сервис + его БД/зависимости | Да — проверяет реальную работу provider'а |
| **Contract** | Совместимость consumer ↔ provider | — |
| **Schema validation** | Соответствие ответа OpenAPI | Да — общая форма API |
| **E2E** | Пользовательский сценарий | Да — несколько критичных сценариев |
| **Performance** | Нагрузка и латентность | Независимо |

## Contract testing для QA

Роль QA-инженера в contract testing:

- Помогает выбрать **критичные interactions** и негативные сценарии.
- Следит за **качеством контрактов**: не слишком жёсткие, не слишком широкие.
- Настраивает **окружение** для provider verification и state handlers.
- Встраивает проверки в **CI/CD** и контролирует `can-i-deploy`.
- Анализирует упавшие verification и помогает командам договориться.

## Итоги

- Идея CDC работает и для событий, и для gRPC/GraphQL.
- Message pacts проверяют **содержимое сообщений**, а не транспорт.
- Контракты дополняют, но не заменяют unit, integration и E2E.
