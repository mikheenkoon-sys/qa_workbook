# Best practices и anti-patterns

Contract testing легко внедрить «формально» и получить хрупкие тесты, которые мешают, а не помогают. Ниже — практики, которые работают, и ловушки, которых стоит избегать.

## Best practices

### 1. Контракт описывает потребности consumer'а
Фиксируйте только то, что клиентский код **реально использует**. Не копируйте весь ответ provider'а.

### 2. Используйте matchers
Тип и формат важнее конкретных значений. Конкретное значение фиксируйте, только если от него зависит логика consumer'а.

### 3. Тестируйте реальный клиентский код
Consumer test должен вызывать **настоящий HTTP-клиент** приложения, а не отдельный «тестовый» fetch.

### 4. Один контракт — одно поведение
Каждая interaction проверяет один сценарий: `GET существующего`, `GET несуществующего`, `POST с ошибкой валидации`.

### 5. Давайте interactions говорящие имена
`uponReceiving("a request for an existing loan")` читается в отчётах и логах; `"test1"` — нет.

### 6. Provider states — минимальные и идемпотентные
Готовьте только данные, нужные interaction. Состояние должно создаваться повторяемо.

### 7. Детерминированное окружение для verification
Фиксированные данные, управляемое время и ID, заглушки внешних сервисов. Никакого общего stage.

### 8. Версия = git SHA, всегда с веткой
Это основа для `can-i-deploy`, pending и WIP pacts.

### 9. Контракты — часть CI
Consumer tests → publish → verification → `can-i-deploy` → `record-deployment`. Без автоматизации контракты быстро устаревают.

### 10. Контракты — повод для общения
Падение verification обсуждается командами. Это не «баг тестов».

## Anti-patterns

| Anti-pattern | Чем плох | Как правильно |
|--------------|----------|---------------|
| **Контракт = снапшот ответа** | Любое безвредное изменение ломает тест | Matchers, только используемые поля |
| **Тестируют бизнес-логику provider'а** | Contract test превращается в медленный integration test | Логику — в unit/integration, контракт — только форма |
| **Mock в consumer test ≠ реальный клиент** | Контракт не проверяет ничего полезного | Вызывайте настоящий клиент |
| **Provider «чинит» verification под себя** | Контракт теряет смысл | Обсуждайте изменение с consumer'ом |
| **Один огромный контракт на всё** | Трудно понять, что сломалось | Небольшие, сфокусированные interactions |
| **Общий stage вместо изоляции** | Flaky, зависит от чужих данных | Изолированный provider с тестовыми данными |
| **Реальные токены в контрактах** | Утечка секретов в Broker | `requestFilter` + secrets из окружения |
| **Безусловный `requestFilter`** | Скрывает негативные auth-сценарии | Условная подмена, sentinel для invalid token |
| **Публикация верификаций с локальной машины** | «Мусорные» результаты в Broker | `publishVerificationResult` только в CI |
| **Игнор pending pacts** | Новые контракты блокируют provider | `enablePending: true` |
| **Контрактов нет, но есть Pact Broker** | Инфраструктура без пользы | Начните с одной критичной пары сервисов |

## С чего начать внедрение

1. Выберите **одну пару** consumer ↔ provider с частыми проблемами интеграции.
2. Напишите 3–5 consumer tests на самые важные interactions.
3. Добавьте provider verification с state handlers.
4. Подключите Pact Broker (или PactFlow) и CI.
5. Добавьте `can-i-deploy` перед деплоем.
6. Расширяйте на другие пары по мере уверенности.

## Чек-лист ревью контракта

- [ ] Тестируется реальный клиент, а не mock.
- [ ] Использованы matchers там, где значение динамическое.
- [ ] Нет лишних полей, которые consumer не читает.
- [ ] Interactions имеют понятные уникальные имена.
- [ ] Provider states описаны и реализованы на стороне provider.
- [ ] Негативные сценарии покрывают только поведение, которое consumer обрабатывает.
- [ ] В контракте нет секретов и реальных персональных данных.
- [ ] Версия и ветка передаются при публикации.

## Метрики здоровья

- Время от публикации контракта до верификации provider'ом.
- Доля деплоев, заблокированных `can-i-deploy` (и были ли они обоснованы).
- Количество breaking changes, пойманных **до** production.
- Доля flaky verification (должна стремиться к нулю).

## Итоги

- Хороший контракт **узкий**, **устойчивый** (matchers) и **автоматизированный** (CI + Broker).
- Contract testing — это про коммуникацию между командами не меньше, чем про тесты.
