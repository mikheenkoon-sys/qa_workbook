# Эволюция контрактов и breaking changes

API не стоит на месте: добавляются поля, меняются форматы, удаляются устаревшие endpoints. Contract testing помогает делать это **безопасно** — но нужно понимать, какие изменения опасны.

## Breaking vs non-breaking

Изменение считается **breaking**, если после него provider перестаёт удовлетворять ожиданиям действующего consumer.

| Изменение | Для consumer | Почему |
|-----------|--------------|--------|
| Добавили **новое** поле в ответ | ✅ Безопасно | Consumer его не использует (если не строгий парсер) |
| Добавили **необязательный** query-параметр | ✅ Безопасно | Старые запросы работают |
| Добавили **новый** endpoint | ✅ Безопасно | Никто пока не вызывает |
| **Удалили** поле из ответа | ❌ Breaking | Consumer ожидает его |
| **Переименовали** поле | ❌ Breaking | Для consumer это удаление + добавление |
| Изменили **тип** (`number` → `string`) | ❌ Breaking | Парсинг ломается |
| Сделали поле запроса **обязательным** | ❌ Breaking | Старые запросы получат 400 |
| Изменили **status code** (`200` → `201`) | ❌ Breaking | Consumer проверяет статус |
| Изменили **path** или **method** | ❌ Breaking | Запросы уйдут в никуда |
| Сузили допустимые **значения** enum | ⚠️ Зависит | Ломает, если consumer их отправляет |
| Расширили enum **в ответе** | ⚠️ Зависит | Ломает, если consumer делает `switch` без default |

## Принцип Postel и «tolerant reader»

> Будь консервативным в том, что отправляешь, и либеральным в том, что принимаешь.

Хороший consumer — **tolerant reader**: читает только нужные ему поля и игнорирует остальные. Тогда provider спокойно добавляет новые поля без ломки контрактов. Строгая десериализация («упасть при неизвестном поле») делает любое расширение API breaking.

## Как менять API безопасно: Expand and Contract

Чтобы убрать или переименовать поле без поломки consumers, делайте это в **три шага** (также называется *parallel change*):

1. **Expand** — provider добавляет **новое** поле (`loanAmount`), оставляя старое (`amount`). Обе версии работают.
2. **Migrate** — consumers по очереди переходят на новое поле и **обновляют контракты**. Broker показывает, кто ещё использует старое.
3. **Contract** — когда ни один контракт не использует `amount`, provider **удаляет** его. Verification подтвердит, что ничего не сломалось.

Именно здесь contract testing раскрывается полностью: вы **не гадаете**, кто использует поле, а видите это в контрактах.

## Что делать при падении verification

```
Verification упала после изменения provider'а
          │
          ├─ Изменение намеренное (breaking)?
          │      └─ Да → expand/contract, согласуйте миграцию с consumer
          │
          ├─ Это баг provider'а (случайно сломали)?
          │      └─ Да → чините provider
          │
          └─ Consumer ожидал то, чего provider не обещал?
                 └─ Да → правьте контракт на стороне consumer
```

Главное правило: **не «подгоняйте» тест**. Падение — повод для разговора между командами.

## Версионирование API и контракты

- Если breaking change неизбежен, выпускайте **новую версию API** (`/v2/loans`) и держите старую, пока её использует хотя бы один контракт.
- Контракт на `/v1/loans` продолжает проверяться до тех пор, пока consumer его публикует.
- Каждый consumer **удаляет** старые interactions, когда мигрирует.

## Deprecation процесс

1. Объявить поле/endpoint устаревшим (документация, `Deprecation`/`Sunset` headers).
2. Проверить по Broker, **какие consumers** его ещё используют.
3. Связаться с командами, договориться о сроках.
4. Удалить, когда `can-i-deploy` и verification зелёные.

## Итоги

- Добавление — обычно безопасно; удаление, переименование и смена типа — breaking.
- Consumers должны быть tolerant readers.
- Expand and Contract — безопасный способ менять API.
- Contract testing показывает, **кто и что реально использует**, и делает deprecation управляемым.
