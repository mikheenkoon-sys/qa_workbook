# Шпаргалка и вопросы для собеседования

Краткая выжимка по всей главе: быстро повторить перед практикой и собеседованием.

## Шпаргалка

```
Consumer test  →  pact-файл  →  Pact Broker  →  Provider verification  →  can-i-deploy
```

| Понятие | В одном предложении |
|---------|---------------------|
| Contract testing | Проверка совместимости двух сервисов по согласованному контракту |
| Consumer | Тот, кто вызывает API |
| Provider | Тот, кто предоставляет API |
| CDC | Consumer описывает ожидания, provider им соответствует |
| Interaction | Ожидаемый запрос и ответ |
| Matcher | Сравнение по типу/формату, а не по значению |
| Provider state | Предусловие данных на стороне provider |
| State handler | Код, создающий это предусловие |
| Provider verification | Воспроизведение interactions на реальном provider |
| Pact Broker | Хранилище контрактов и результатов верификации |
| `can-i-deploy` | Можно ли безопасно деплоить эту версию |
| `requestFilter` | Hook, меняющий verification request (например, токен) |
| Pending pact | Новый контракт, падение которого не ломает build provider'а |
| Tolerant reader | Consumer, читающий только нужные поля |

## Команды и конфигурация

```bash
# Опубликовать контракты
pact-broker publish ./pacts --consumer-app-version "$GIT_SHA" --branch "$GIT_BRANCH"

# Можно ли деплоить
pact-broker can-i-deploy --pacticipant web-app --version "$GIT_SHA" --to-environment production

# Зафиксировать деплой
pact-broker record-deployment --pacticipant web-app --version "$GIT_SHA" --environment production
```

## Вопросы и ответы

### Что такое contract testing и какую проблему оно решает?
Это проверка того, что consumer и provider совместимы по согласованному контракту. Решает проблему **незаметных breaking changes** в API между независимо разрабатываемыми сервисами — быстрее и локализованнее, чем E2E.

### Чем contract testing отличается от E2E и integration-тестов?
Контрактные тесты проверяют **границу** между двумя сервисами изолированно. Integration-тесты проверяют сервис с реальными зависимостями, E2E — весь пользовательский сценарий. Контракты быстрее и точнее показывают место проблемы, но не доказывают работу всей системы.

### Что такое consumer-driven contracts?
Подход, при котором контракт формируется **со стороны consumer** и описывает только то, что ему реально нужно. Provider обязан соблюдать все такие контракты, но свободен менять остальное.

### Почему consumer test не доказывает совместимость?
Он работает с **mock provider**. Совместимость доказывает только provider verification на реальном сервисе.

### Зачем нужны matchers?
Чтобы контракт проверял **тип и формат** данных, а не конкретные значения. Без них тесты становятся хрупкими.

### Что такое provider states?
Предусловия данных для конкретной interaction (например, «кредит 123 существует»). Описываются в consumer test через `given`, реализуются в `stateHandlers` на стороне provider.

### Что произойдёт, если provider вернёт 500 вместо ожидаемого 200?
Verification **упадёт** — фактический статус не совпадает с контрактом.

### Что такое breaking change? Приведите примеры.
Изменение, после которого provider не удовлетворяет ожиданиям действующего consumer: удаление или переименование поля, смена типа, смена статуса или пути, новое обязательное поле запроса. Добавление нового поля обычно безопасно.

### Как безопасно удалить поле из API?
Через **expand and contract**: добавить новое поле, дождаться миграции consumers (по контрактам и Broker видно, кто использует старое), затем удалить старое.

### Зачем нужен Pact Broker и can-i-deploy?
Broker хранит контракты и результаты верификации. `can-i-deploy` проверяет по матрице версий, что деплой конкретной версии не сломает consumers/providers в целевом окружении, и блокирует небезопасный деплой.

### Что такое pending и WIP pacts?
**Pending** — новый контракт, ни разу не прошедший верификацию; его падение не ломает сборку provider'а. **WIP** — контракты из feature-веток, которые provider подхватывает автоматически.

### Зачем нужен requestFilter?
Чтобы изменить исходящий verification request, например подставить валидный токен. Нельзя подменять токен безусловно — негативные auth-сценарии потеряют смысл. Используйте sentinel для invalid token.

### Как хранить токены для verification?
В переменных окружения CI или secret manager, но не в коде и не в pact-файле. `requestFilter` берёт токен оттуда.

### Чем contract testing отличается от schema validation (OpenAPI)?
Схема описывает, что provider **может** вернуть. Контракт описывает, что **нужно** конкретным consumers. Контракт ловит поломки, которые для схемы выглядят допустимыми.

### Что такое async/await и что вернёт async-функция без await?
`async`-функция всегда возвращает **Promise**. Вызов без `await` даёт Promise, который может быть ещё не завершён; rejected Promise при `await` выбрасывает исключение.

### Когда contract testing не стоит применять?
Для монолита с единым деплоем, одного consumer и provider в одном репозитории или публичного API с неизвестными consumers (лучше OpenAPI + schema validation).
